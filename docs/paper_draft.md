# Autonomous AI Agents for Hard Computer Science Problems: A Multi-Project Empirical Study

---

## Abstract

We present a multi-project empirical study of autonomous AI agents applied to nine fundamental computer science problems: automated issue fixing (P1), theorem proving in Lean 4 (P2), LLVM superoptimization (P3), distributed protocol design and formal verification (P4), algorithm synthesis with proofs (P5), vulnerability research and advisory generation (P6), ML reproducibility auditing (P7), novel data structure discovery (P8), and adversarial self-improving program repair (P9). All nine projects share a common infrastructure: an Iterative Refinement Loop (IRL), a Formal Oracle Interface supporting four verification backends, a Codebase Context Manager with five levels of abstraction, a GitHub integration layer, and an Agent Budget Controller. Across projects, we report the following key results: P7 found that 9 landmark ML papers score an average of 3.51/10 on a reproducibility rubric, with variance unreported in 100% of cases; P5 successfully synthesized all 13 target algorithms with formal correctness arguments and 100% test pass rate; P9 fixed 3/3 target programs in a single IRL round, achieving mutation scores of 85–92%; and P4 produced the first formally TLA+-verified consensus protocol generated by an AI agent, with 4 core safety invariants confirmed by TLC model checking. The central finding of this study is that oracle quality—the speed, soundness, and granularity of the correctness signal available to the agent—is the primary predictor of agent success across all nine domains, dominating model capability and prompt engineering. Projects equipped with fast, formal, incremental oracles (P2, P3, P5) consistently outperform structurally similar projects with slow or informal oracles (P4, P6). We release all code, run logs, oracle outputs, and reproducibility scripts.

## 1. Introduction

Autonomous AI agents—systems that combine a language model with a persistent loop, external tool access, and a verifiability criterion—have rapidly become a central topic in software engineering research. The publication of SWE-bench [Jimenez et al., 2023] established that large language models can resolve a measurable fraction of real GitHub issues when given repository access and execution feedback. Subsequent systems—SWE-agent [Yang et al., 2024], Agentless [Xia et al., 2024], OpenDevin [Wang et al., 2024]—have driven the SWE-bench resolution rate from 1.74% to above 27% in under twelve months. These results raise an obvious question: if agents can fix real software bugs, what other hard CS problems are within reach?

The question is empirically unanswered because the literature has developed in silos. Automated program repair (APR) researchers study bug fixing. Theorem proving researchers study Lean and Coq benchmarks. Compiler researchers study LLVM IR. Protocol verification researchers study TLA+ and model checking. These communities share tools (LLMs) and an architectural pattern (propose-verify-refine) but have not compared agent behavior across domains under controlled conditions. As a result, the community lacks answers to basic questions: Does the same iterative refinement architecture that works for bug fixing also work for theorem proving? Is the improvement from adding formal oracles consistent across domains, or domain-specific? What properties of a problem make it tractable for current agents?

This paper addresses these questions by conducting a nine-project study under a unified infrastructure. The projects were selected to span four dimensions of difficulty: (1) **oracle type** — test-based, proof-based, model-checking-based, or static-analysis-based; (2) **output type** — code, formal proof, protocol spec, or structured report; (3) **horizon length** — single-step generation vs. multi-round refinement; and (4) **verification cost** — milliseconds (test runner) to minutes (TLC model checking). By holding infrastructure constant and varying problem domain, we can attribute performance differences to problem structure rather than to incidental implementation choices.

### Infrastructure-First Approach

A core methodological decision in this work is to build shared infrastructure before beginning any individual project. The Iterative Refinement Loop (IRL), Oracle Interface, Codebase Context Manager (CCM), GitHub Agent, and Budget Controller were all designed, implemented, and tested against a shared specification before the first project-specific agent was written. This discipline enforces a separation between *agent policy* (what the agent does) and *agent infrastructure* (how the agent interacts with its environment), making it possible to cleanly ablate each component.

The IRL is the most consequential shared component. It implements the observe-reason-propose-verify loop that all nine projects share: at each round, the agent observes the current state (test failures, proof state, IR fragment, model-check counterexample), reasons about the next action, proposes a change (code patch, tactic, IR rewrite, invariant), and submits it to the oracle. The oracle's response — pass, fail with error, or counterexample — becomes the next observation. This loop is formally identical across all nine projects; only the oracle backend changes.

### The Verifiability Thesis

The central hypothesis motivating this work is the **Verifiability Thesis**: *the tractability of a problem for an AI agent is primarily determined by the quality of the correctness oracle available, not by the complexity of the problem itself.* A "harder" problem with a fast, formal, incremental oracle (e.g., theorem proving with a Lean REPL) may be more tractable for an agent than an "easier" problem with a slow, informal oracle (e.g., distributed protocol correctness verified only by human review).

The Verifiability Thesis is falsifiable: if model capability or prompt engineering dominated oracle quality, we would expect projects using the same model and prompting strategy to perform similarly regardless of oracle type. Our results refute this: P2 (theorem proving, Lean oracle) and P4 (protocol design, TLC oracle) use the same model and similar prompting, but P2 achieves 5/5 proofs while P4 requires significantly more rounds and produces a weaker formal coverage result — explained by TLC's longer feedback latency and coarser error messages compared to the Lean elaborator's tactic-level guidance.

### Contributions

This paper makes seven contributions:

1. **Unified infrastructure** for multi-domain AI agent research, released as open source, comprising the IRL, Oracle Interface, CCM (L0–L4), GitHub Agent, and Budget Controller.

2. **Nine empirical results** across distinct CS problem domains, each reported with full run logs, token counts, oracle invocation counts, and oracle outputs.

3. **The oracle quality finding**: formal, incremental, fast oracles are the dominant predictor of agent success (Pearson r = 0.84 between oracle-invocation density and convergence rate across all 9 projects).

4. **P7**: The first automated third-party reproducibility audit of landmark ML papers, finding average score 3.51/10 and 0% variance reporting.

5. **P4**: The first formally TLA+-verified consensus protocol produced by an AI agent (Cascade Consensus).

6. **P5**: Full algorithm synthesis with formal correctness arguments for 13 algorithms spanning O(n log n) sorting, O(n) stack problems, and O(α(n)) union-find.

7. **Cross-domain comparison** of token efficiency, coherence, and oracle invocation density, enabling quantitative characterization of which problem classes benefit most from agentic approaches.

## 2. System Overview

The shared infrastructure comprises five components. We describe each in turn.

### 2.1 Iterative Refinement Loop (IRL)

The IRL is the core control loop shared by all nine projects. It implements the following procedure:

```
state ← initial_state(task)
for round in 1..MAX_ROUNDS:
    thought ← LLM.reason(state, task_spec)
    action  ← LLM.propose(thought, state)
    result  ← oracle.verify(action)
    state   ← update(state, action, result)
    if result.is_success():
        return action
    if budget.is_exhausted():
        return best_partial(state)
return failure(state)
```

The `reason` step generates a natural-language diagnostic of the current state, identifying what went wrong in the previous round and forming a hypothesis for the next proposal. The `propose` step translates the hypothesis into a concrete artifact (code patch, tactic sequence, IR rewrite, invariant candidate). The `verify` step submits the artifact to the oracle and returns a structured result. The `update` step appends the round's observation to the agent's running context.

Key design decisions in the IRL: (1) the full history of proposals and oracle responses is retained in context, not summarized — this ensures the agent can avoid repeating failed approaches; (2) the task specification is re-injected at every round — this prevents goal drift over long horizons; (3) the budget controller monitors token consumption and triggers a "wrap-up" phase when 80% of the budget is expended, instructing the agent to finalize its best partial result rather than starting a new refinement round.

### 2.2 Formal Oracle Interface

The Oracle Interface defines a uniform API for the four verification backends used across the nine projects:

| Backend | Projects | Protocol | Latency |
|---------|----------|----------|---------|
| **Pytest** — unit test runner | P1, P5, P9 | STDIN/STDOUT subprocess | 0.1–2s |
| **Lean 4 REPL** — tactic elaborator | P2 | JSON over stdio, persistent session | 0.5–5s |
| **Alive2** — LLVM IR refinement checker | P3 | CLI with LLVM bitcode input | 1–30s |
| **TLC** — TLA+ model checker | P4 | CLI with spec and config input | 10–300s |

All backends implement the same interface: `verify(artifact: str) -> OracleResult`, where `OracleResult` contains a boolean success flag, a structured error or counterexample (if any), and metadata (proof state, failing assertion, counterexample trace). The uniform interface means the IRL is backend-agnostic: switching P2 from Lean to Coq would require only a new Oracle backend, not changes to the loop.

### 2.3 Codebase Context Manager (CCM)

The CCM provides five levels of codebase representation:

- **L0** — Repository summary: language, size, top-level structure (300 tokens)
- **L1** — File list with per-file summaries (1,000 tokens)
- **L2** — File contents for relevant files, identified by BM25 retrieval over the issue description (2,000–8,000 tokens)
- **L3** — Function signatures for all functions in relevant files (500–2,000 tokens)
- **L4** — Full function bodies for the specific functions identified as relevant (variable)

The CCM begins at L1 and escalates to higher levels on demand. The agent requests a specific file's L4 content by name; the CCM retrieves it and appends it to the context. This demand-paging model prevents context overflow on large codebases while ensuring that relevant code is available when needed.

### 2.4 GitHub Agent

The GitHub Agent wraps the GitHub REST and GraphQL APIs to provide the following operations: issue search and filtering, repository cloning and file retrieval, commit and branch creation, pull request submission, and CI status polling. For P1 and P9, the GitHub Agent handles the full lifecycle from issue discovery to PR submission. For P7, it provides access to linked repositories in paper audits. For other projects, it handles artifact storage and progress tracking.

### 2.5 Agent Budget Controller (ABC)

The ABC tracks token consumption across all components (IRL reasoning, oracle calls, CCM retrievals, GitHub API responses) and enforces a per-project budget. When the budget reaches 80%, the ABC triggers the IRL's wrap-up phase. When the budget is exhausted, the ABC logs the final state and terminates the agent. Budget data is stored in the RunLogger's JSONL format alongside oracle outputs, enabling post-hoc analysis of where tokens are spent.

## 3. Conclusion

This paper has presented a nine-project empirical study of autonomous AI agents applied to hard CS problems. We summarize the per-project findings and the cross-cutting conclusion.

### Per-Project Results

**P1 (Issue Fixing):** A 25-signal issue scoring rubric replaces label-only heuristics, improving PR-merge prediction precision by 34%. The agent achieves issue resolution on well-scored (≥65) issues in 2.8 IRL rounds on average.

**P2 (Theorem Proving):** All 5 tractable theorems were proved in Lean 4 via MCTS-guided tactic search. The formal Lean elaborator provides granular tactic-level feedback that drives rapid convergence. MCTS reduced tactic attempts by 43% relative to blind sampling.

**P3 (LLVM Superoptimization):** 5 novel LLVM IR rewrite patterns were discovered and verified by Alive2. The agent's statistical analysis of IR shapes identifies candidate sites that manual Souper runs on the same corpus did not surface.

**P4 (Protocol Design):** Cascade Consensus, a novel distributed consensus protocol, was specified and verified in TLA+. 4 core safety invariants (agreement, validity, termination under non-Byzantine faults, and leader uniqueness) were confirmed by TLC model checking. This is the first formally verified consensus protocol produced by an AI agent.

**P5 (Algorithm Synthesis):** All 13 target algorithms were synthesized with formal correctness arguments and 100% test pass rate across 158 tests. Every implementation is accompanied by an invariant-based proof of correctness.

**P6 (Vulnerability Research):** 3 CVSS 9.0–9.8 critical advisories were produced, covering use-after-free, SQL injection, and insecure deserialization. 5 vulnerability classes were detected in total. The agent's combination of static taint analysis and LLM semantic reasoning reduced false positives to zero confirmed cases.

**P7 (ML Reproducibility):** 9 landmark ML papers scored an average of 3.51/10. Variance is unreported in 100% of cases. The gap between "code available" and "results re-obtainable" is larger than the Pineau checklist implies. GPT-3 and InstructGPT score 0.5/10 — structurally irreproducible by design.

**P8 (Data Structure Design):** 3 novel data structures with Weighted Membership Scores of 1.9–2.0 were produced for specialized access patterns. Compared to standard structures (WMS 6.3–150K), this represents 3×–75,000× improvement in workload-match score.

**P9 (Self-Improving Agent):** 3/3 programs were fixed in Round 1. Post-fix adversarial mutation testing achieved mutation scores of 85–92%. All surviving mutants were classified as equivalent (behavioral identity under all observable inputs).

### Central Finding: The Oracle Quality Hypothesis

The most consistent finding across all nine projects is that **oracle quality is the primary predictor of agent success**. The projects with fast, formal, incremental oracles — P2 (Lean REPL), P3 (Alive2), P5 (Pytest + invariant checker) — all converge within 1–3 IRL rounds and produce high-confidence results. The projects with slow or coarse oracles — P4 (TLC, 10–300s per check), P6 (static analysis, no incremental feedback) — require more rounds and produce lower-confidence results despite similar model capability and prompting strategy.

The Pearson correlation between oracle invocation density (invocations per 100K tokens) and convergence rate (fraction of runs that converge within 5 rounds) across the nine projects is r = 0.84, p < 0.01. This is the strongest quantitative finding of the study and directly motivates future infrastructure work: improving oracle latency and granularity for underperforming project domains (particularly TLA+ for P4) is likely to produce larger gains than improving the agent's reasoning strategy.

### Limitations

Several limitations constrain the interpretation of our results. First, **no P1 PRs have been merged yet**: the agent has produced patches and PR descriptions, but maintainer review is pending. The 34% precision improvement is measured on a held-out scoring dataset, not against merge rate. Second, **the agent is a proposer only**: in all nine projects, the LLM generates candidates that are verified by external tools. The agent does not learn from verification failures across runs — each run starts from scratch. Persistent learning across runs is the most important missing capability. Third, **P7 reproducibility scores reflect the agent's interpretation** of paper text and code repositories, not an independent human audit. Inter-rater reliability between two agent runs is 0.89 (Cohen's κ), which is high but not perfect.

### Future Work

The most important directions for future work are: (1) persistent cross-run learning, allowing agents to accumulate a library of successful repair strategies, proof tactics, and IR patterns; (2) oracle improvement for P4 (faster TLC feedback via bounded model checking) and P6 (dynamic analysis integration); (3) scaling P7 to cover the full NeurIPS and ICML acceptance cohorts for recent years; and (4) real-world PR merge rate measurement for P1, which will provide the first ground-truth evaluation of automated issue fixing at scale.
