# Security Advisories — P6 Autonomous Vulnerability Research

## SA-2024-001: Off-by-One Heap Buffer Overflow in String Allocation

**CVSSv3.1:** 9.8 Critical  
**Vector:** `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`  
**CWE:** CWE-193 (Off-by-One Error), CWE-122 (Heap-based Buffer Overflow)

### Vulnerable Pattern
```c
char *buf = malloc(strlen(input));  // allocates strlen(input) bytes
strcpy(buf, input);                 // writes strlen(input)+1 bytes (null terminator overflow)
```

### Root Cause
`strlen()` returns byte count *excluding* the null terminator. `strcpy()` copies *including* the null terminator. The null byte lands one byte past the allocation, corrupting the next heap chunk's metadata header (`size`/`PREV_INUSE` field in ptmalloc).

### Exploitability
**High.** Single-null-byte heap overflows enable House of Einherjar on glibc < 2.32. The corrupted metadata bit can trigger controlled heap consolidation leading to arbitrary heap write → RCE.

### Real-World CVEs
| CVE | Software | Year |
|-----|----------|------|
| CVE-2016-6289 | PHP 7.x `zend_virtual_cwd.c` | 2016 |
| CVE-2021-3156 | sudo (Baron Samedit) | 2021 |

### Correct Patch
```c
// Option A: explicit +1
char *buf = malloc(strlen(input) + 1);
strcpy(buf, input);

// Option B: strdup (preferred)
char *buf = strdup(input);
if (!buf) return NULL;
```

## SA-2024-002: Integer Overflow → Heap Overflow in Size Computation

**CVSSv3.1:** 9.8 Critical  
**Vector:** `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`  
**CWE:** CWE-190 (Integer Overflow), CWE-131 (Incorrect Buffer Size Calculation)

### Vulnerable Pattern
```c
// count and element_size are 32-bit; multiplication wraps before widening to size_t
size_t total = count * element_size;   // 0x40000001 * 4 = 0x4 (wraps!)
void *buf = malloc(total);             // allocates 4 bytes
memcpy(buf, src, total);              // copies 4GB+ — massive overflow
```

### Root Cause
32-bit × 32-bit multiplication occurs in 32-bit arithmetic even when the result is assigned to `size_t`. The overflow is defined behavior for unsigned types, so the compiler emits no warning.

### Exploitability
**Critical.** Unbounded heap write with attacker-controlled content. Bypasses all heap hardening. ASLR does not meaningfully limit a multi-gigabyte write.

### Real-World CVEs
| CVE | Software | Year |
|-----|----------|------|
| CVE-2022-0185 | Linux kernel `legacy_parse_param()` | 2022 |
| CVE-2019-11477 | Linux kernel TCP SACK | 2019 |

### Correct Patch
```c
// Option A: calloc (overflow-safe by POSIX spec)
void *buf = calloc(count, element_size);

// Option B: explicit guard
if (element_size != 0 && count > SIZE_MAX / element_size) return NULL;
size_t total = count * element_size;

// Option C: compiler builtin (GCC 5+, Clang 3.8+)
size_t total;
if (__builtin_mul_overflow(count, element_size, &total)) return NULL;
```

## SA-2024-003: Use-After-Free via Stale Cache Pointer

**CVSSv3.1:** 9.0 Critical  
**Vector:** `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H`  
**CWE:** CWE-416 (Use After Free), CWE-825 (Expired Pointer Dereference)

### Vulnerable Pattern
```c
// Path A: frees object but does NOT remove cache entry
object_t *obj = hashtable_get(cache, key);
free(obj);                    // cache["key"] still holds dangling pointer

// Path B: dereferences the dangling pointer
object_t *stale = hashtable_get(cache, key);  // returns freed pointer
stale->data = process(stale->data);           // USE-AFTER-FREE
```

### Root Cause
`free()` does not modify the pointer value and does not invalidate cache entries. The allocator may immediately recycle the freed chunk, allowing an attacker to control the memory at the dangling address.

### Exploitability
**Critical.** With glibc tcache: deterministic heap recycling. An attacker triggering Path A (delete) then a same-size allocation then Path B (read) can forge an `object_t` at the recycled address. If `object_t` contains function pointers → arbitrary code execution.

### Real-World CVEs
| CVE | Software | Year |
|-----|----------|------|
| CVE-2020-8616 | BIND 9 DNS resolver | 2020 |
| CVE-2021-30551 | Google Chrome V8 | 2021 |
| CVE-2022-3038 | Google Chrome Network Service | 2022 |

### Correct Patches
```c
// Strategy 1: remove-before-free (simplest)
object_t *obj = hashtable_remove(cache, key);  // atomic remove+return
if (obj) free(obj);  // no alias remains

// Strategy 2: reference counting
void obj_release(object_t *obj) {
    if (atomic_fetch_sub(&obj->refcount, 1) == 1)
        free(obj);
}

// Strategy 3: epoch-based reclamation (RCU)
// rcu_read_lock(); ... rcu_read_unlock();
// call_rcu(&obj->rcu_head, free_callback);
```
